Solving Ambiguous Upstream Routing in Multi-Level Git Fork Networks

Author: Amir Tahani
Target: gitlab-org/cli
Merge Request: MR !4432
Reading Time: 6 min read
GitLab CLI Merge Request !4432: fix(mr create): use --repo as source project when local remote is not a fork →

Closes Issue #8666. Resolves HTTP 422 errors when invoking `glab mr create --repo` from unrelated repositories while protecting multi-level fork networks from unintended branch redirects.

The Problem: Unintended Remote Coupling in Git CLI Tools

In enterprise developer environments, developers frequently work inside mono-repos, personal scratchpads, or unrelated project folders when attempting to submit Merge Requests to remote repositories using CLI commands like: 

glab mr create --repo group/project-b --source-branch feature-x

Prior to MR !4432, the CLI's initialization phase (PreRun) unconditionally assumed that the local directory's git remote was the intended headRepo (source project). If the local project was not a fork of group/project-b, the API rejected the payload with: 

422 Unprocessable Entity: Source project is not a fork of the target project

The Subtlety of Multi-Level Fork Networks

A naive fix would simply force sourceProject = targetProject whenever the local remote does not match --repo. However, GitLab supports sophisticated fork networks:

  • Forks of Forks: Developer Fork → Team Staging Fork → Upstream Canonical.
  • Sibling Forks: Multiple forks within an engineering department collaborating on a common feature branch.
  • Direct Pushes: When flags like --push or --fill are supplied, switching the source project could inadvertently attempt a git push directly into upstream canonical instead of the developer's personal fork!

The Architectural Solution in MR !4432

Collaborating with GitLab CLI maintainers, we engineered a guarded resolution mechanism in internal/commands/mr/create/mr_create.go: 

// Only redirect when local project is completely unrelated
isUnrelated := !headRepoExplicit &&
    baseRepoOverridden &&
    o.MRCreateTargetProject == "" &&
    o.SourceProject != nil &&
    o.TargetProject != nil &&
    o.SourceProject.ForkedFromProject == nil &&
    (o.TargetProject.ForkedFromProject == nil ||
     o.TargetProject.ForkedFromProject.ID != o.SourceProject.ID) &&
    o.SourceProject.PathWithNamespace != o.TargetProject.PathWithNamespace

if isUnrelated {
    o.io.LogInfof("Using %s as the source project: %s is not a fork of it.\n",
        o.TargetProject.PathWithNamespace, o.SourceProject.PathWithNamespace)
    o.SourceProject = o.TargetProject
    o.headRepo = baseRepo
}

Key Architectural Invariants Enforced:

  1. Fork Preservation: If o.SourceProject.ForkedFromProject != nil, the project belongs to a fork hierarchy and is never redirected.
  2. User Transparency: We emit an informative log via o.io.LogInfof so users are explicitly notified when an unrelated source project is defaulted.
  3. Deprecated Flag Protection: Invocations explicitly using deprecated --target-project bypass redirect logic to maintain backwards compatibility.

Lessons in Developer Ergonomics

CLI tools must strike a delicate balance between DWIM ("Do What I Mean") automation and strict developer safety. When inferring state from local git remotes, always distinguish between completely unrelated projects and legitimate complex fork topologies.
