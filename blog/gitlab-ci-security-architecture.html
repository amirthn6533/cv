Pipeline Token Allowlist Boundaries: Resolving 403 Forbidden in GitLab Security MR Workflows

Author: Amir Tahani
Target: gitlab-org/modelops/.../ai-assist
Merge Request: MR !8051
Reading Time: 5 min read
AI-Assist Merge Request !8051: ci: skip danger-review on security-to-canonical merge MRs →

Resolves Issue #3731. Eliminates CI pipeline blockers during critical security patch releases caused by cross-project token isolation boundaries.

The Background: GitLab Security Release Topology

To patch critical zero-day vulnerabilities in GitLab and its AI Gateway infrastructure without exposing vulnerabilities prematurely, engineering teams operate on an isolated private mirror: gitlab-org/security/modelops/applied-ml/code-suggestions/ai-assist.

Once patches pass private review and security deadlines arrive, a release manager opens a Security-to-Canonical Merge Request to merge the confidential security branch into the public canonical repository (gitlab-org/.../ai-assist:main).

The Failure Mechanism: CI Job Token Isolation

Under modern GitLab CI architecture, Job Token Allowlist policies prevent CI jobs running in one project from reading resources in another project unless explicitly authorized. When a canonical pipeline initiated a danger-review job for a security MR:

  1. The Danger bot attempted to execute a git fetch against the source security repository using the canonical job's transient token.
  2. The security repository's allowlist rejected the unauthorized token, resulting in an unrecoverable HTTP 403 Forbidden git fetch failure.
  3. This completely halted canonical security merges, forcing manual pipeline overrides during high-pressure release windows.
💡 The Core Insight

Security merges are authored and vetted internally by senior security engineers. Automated Danger bot style checks (which verify changelog entries and commit formatting) provide zero utility during a security backport, while actively obstructing the deployment of critical fixes.

The Solution: Declarative CI Scoping Rules

In Merge Request !8051, we introduced an upstream conditional rule to the danger-review component in .gitlab/ci/danger.gitlab-ci.yml: 

danger-review:
  rules:
    - if: '$CI_MERGE_REQUEST_SOURCE_PROJECT_PATH =~ /^gitlab-org\/security\//'
      when: never
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: on_success

By utilizing GitLab CI's regex pattern matching against $CI_MERGE_REQUEST_SOURCE_PROJECT_PATH, pipelines seamlessly bypass Danger invocation for all security forks while retaining full automated review enforcement for public developer contributions and community forks.

Engineering Lessons for Large Scale CI/CD

  • Respect Zero-Trust Boundaries: Rather than weakening job token allowlists to permit cross-namespace token traversal, identify jobs whose premises are invalid across boundary lines and omit them declaratively.
  • Protect Release Velocity: Critical security release workflows must be resilient against cosmetic linting failures and external token boundaries.
  • Regex Precision: When filtering CI project paths, anchor regex strings (^gitlab-org\/security\/) to prevent accidental collisions with third-party namespace structures.
