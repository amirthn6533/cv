Contributing to GitLab: Architectural Lessons from 4 Open-Source Merge Requests

Author: Amir Tahani (@amirthn6533)
Location: Sofia, Bulgaria
Platforms: GitLab | GitHub

Introduction

Contributing effectively to world-class open-source codebases like GitLab requires more than writing functional code—it demands strict adherence to system contracts, rigorous unit test isolation, and forward-looking architecture.

Over the past few days, I authored and refined four distinct production Merge Requests across gitlab-org/cli, gitlab-org/gitlab-pages, and gitlab-org/modelops/ai-assist. Here is a technical breakdown of each challenge, how we solved it, and the engineering principles reinforced along the way.

CLI 1. Shared ID Parsing & Subtest Isolation in GitLab CLI Approved

Merge Request: gitlab-org/cli!4425 (Resolves #8691)

The Challenge

Across 18 commands in glab (covering runner, runnercontroller, deploy-token, and container_registry), numeric ID arguments were parsed using raw strconv.ParseInt(args[0], 10, 64). When a user accidentally supplied an invalid string like "abc", the descriptive error was discarded in ExitError.Details, and users saw a bare strconv.ParseInt: parsing "abc": invalid syntax. Even worse, 0 and negative integers slipped past parsing and produced confusing 404 API errors.

The Architectural Solution

We engineered a shared helper cmdutils.ParseID(value, name string) (int64, error) that enforces id >= 1 and formats structured errors: 

// internal/cmdutils/parse_id.go
func ParseID(value, name string) (int64, error) {
    id, err := strconv.ParseInt(value, 10, 64)
    if err != nil || id < 1 {
        return 0, fmt.Errorf("invalid %s: %q", name, value)
    }
    return id, nil
}

Following review recommendations from GitLab Duo and maintainer Rane Hebden, we refactored unit test suites using isolated t.Run subtests with distinct command executions. The change touched 25 packages, passed 100% of unit tests, and was formally approved for merge.

CLI 2. Preserving Multi-Level Fork Networks in `glab mr create` Reviewed (19.7 Milestone)

Merge Request: gitlab-org/cli!4432 (Resolves #8666)

The Challenge

When executing glab mr create --repo <target> from inside an unrelated local repository clone, the CLI previously resolved the source project from the local remote, causing GitLab API to reject the request with 422 Source project is not a fork of the target project.

Refining for Complex Fork Hierarchies

While naive solutions simply redirected source projects, GitLab maintainer Jay McCure noted that multi-level fork networks (fork-of-a-fork or sibling forks) allow valid cross-fork merge requests. Redirecting them silently would push branches into upstream repositories unexpectedly.

We refined the redirection boundary to verify both ancestors and descendents: 

if !o.headRepoExplicit && o.baseRepoOverridden && o.MRCreateTargetProject == "" && o.SourceProject.ID != o.TargetProject.ID {
    isTargetForkOfSource := o.TargetProject.ForkedFromProject != nil && o.TargetProject.ForkedFromProject.ID == o.SourceProject.ID
    if o.SourceProject.ForkedFromProject == nil && !isTargetForkOfSource {
        o.io.LogInfof("Using %s as the source project: %s is not a fork of it.\n", o.TargetProject.PathWithNamespace, o.SourceProject.PathWithNamespace)
        o.SourceProject = o.TargetProject
        headRepo = baseRepo
    }
}

We accompanied this with table-driven tests verifying 10 distinct cases, including GITLAB_REPO / GITLAB_HEAD_REPO environment variables and explicit flag overrides.

GitLab Pages 3. Enforcing Project Prefix Cookie Path Security on Reauth

Merge Request: gitlab-org/gitlab-pages!1387 (Resolves #1223)

The Challenge

In GitLab Pages with feature.ProjectPrefixCookiePath enabled, user authentication cookies must be strictly scoped to the project namespace (e.g., /namespace/project). While normal sessions preserved this prefix, invalid token clearance in checkResponseForInvalidToken reset the cookie path to /namespace, creating session leakage risks between projects sharing a namespace.

The Solution

We centralized cookie path derivation into setSessionProjectPrefixPath(session, r, d) and ensured it is applied across token invalidation and re-authentication lifecycles. Following maintainer Joe Shaw's review, we verified strict path assertion across HTTP response cookies.

AI Gateway 4. Pipeline Optimization for Canonical Security Mirrors

Merge Request: ai-assist!8051 (Resolves #3731)

The Challenge

Security-to-canonical merge requests originating from gitlab-org/security/... suffered from 403 Forbidden errors when canonical CI pipelines attempted to run the danger-review component, due to GitLab job token allowlist boundaries.

In collaboration with maintainer Igor Drozdov, we updated the CI rule logic so internal pipeline validations are preserved while skipping danger checks exclusively on restricted security-to-canonical merges.

Key Takeaways for Open-Source Contributors

  1. Focus on Concrete Quick-Wins: The best entry points into mature repositories are well-scoped maintenance tasks and bug fixes with clear reproduction criteria.
  2. Embrace Review Feedback: Maintainers provide invaluable architectural insights into edge cases like fork networks and authentication scoping. Addressing comments promptly builds immense community trust.
  3. Automate Verification: Comprehensive unit testing and linting before pushing ensures maintainers spend their time reviewing architectural design rather than debugging syntax.
