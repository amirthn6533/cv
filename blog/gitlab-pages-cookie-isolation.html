Securing Multi-Tenant Static Hosting: Project-Prefix Cookie Path Isolation in GitLab Pages

Author: Amir Tahani
Target: gitlab-org/gitlab-pages
Merge Request: MR !1387
Reading Time: 6 min read
GitLab Pages Merge Request !1387: Auth: preserve project prefix cookie path on reauth clear and invalid token →

Addresses GitLab Issue #1223. Prevents session cookie leakage across multi-tenant group projects hosted under shared GitLab Pages domains.

The Challenge: Multi-Tenancy on Shared Domains

In modern cloud environments, serving user-generated static websites under a common parent domain (such as group.gitlab.io/project-a and group.gitlab.io/project-b) presents profound session security challenges. Without strict cookie path scoping, an authentication session intended exclusively for a private repository's documentation site can inadvertently leak to an untrusted neighboring project within the same namespace.

To solve this, GitLab Pages introduces the feature flag feature.ProjectPrefixCookiePath. When activated, every session cookie generated during OAuth flows is bound specifically to the project's URL prefix (e.g., /project-a/) rather than root /.

The Subtle Architectural Defect (Issue #1223)

While investigating authentication re-negotiations in GitLab Pages, we identified an insidious edge case in session state preservation:

  1. When a request enters the authentication middleware, getSessionFromStore parses the session and normalizes the path prefix: 
    session.Options.Path = "/" + namespaceInPath
  2. During standard re-authentication (reauthenticateExpiredSession), Pages correctly called session.appendPath(requestProjectPrefix(r, d)) prior to committing the response.
  3. However, in two critical failure and cleanup pathways—clearReauthMarkerOnSuccess and checkResponseForInvalidToken—Pages invoked session.Save(r, w) directly without appending the project prefix!
⚠️ The Security Consequence

Whenever a token expired or an invalid token was discarded, the browser received a Set-Cookie header with a widened path scoped merely to /group instead of /group/project-subpath. This degraded cookie isolation across sibling projects, potentially exposing authenticated session tokens to unauthorized project pages in the same group.

The Solution: Centralized Prefix Scoping

To eliminate this discrepancy, we abstracted the path-resolution logic into a dedicated helper and applied it consistently across all session mutations: 

func setSessionProjectPrefixPath(session *sessions.Session, r *http.Request, d *domain.Domain) {
    if !feature.ProjectPrefixCookiePath.Enabled() {
        return
    }

    prefix := requestProjectPrefix(r, d)
    if prefix != "" {
        session.Options.Path = session.Options.Path + prefix
    }
}

By calling setSessionProjectPrefixPath() before every session.Save(r, w) invocation, we guaranteed that regardless of whether a session is being established, refreshed, cleared, or invalidated, the resulting HTTP cookie remains strictly bound to the exact project boundary.

Key Takeaways for Go Systems Architects

  • Cookie Scope Invariance: Cookie boundaries must be enforced consistently across all lifecycle stages—especially during error recovery and session termination routines.
  • Explicit Helper Extraction: Delegating security-sensitive header mutations to centralized functions eliminates copy-paste oversights across distributed HTTP handlers.
  • Integration Verification: Comprehensive unit and mock tests should inspect the actual Set-Cookie header strings to confirm path parameters adhere to expected prefix patterns.
